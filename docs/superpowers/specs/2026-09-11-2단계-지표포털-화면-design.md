**상위 스펙:** `docs/superpowers/specs/2026-09-10-노동시장-지표포털-design.md`
**1단계 산출:** 관문 통과 (일치 29,558 · 불일치 0 · 면제 3 · **99.990%**)
**목표 형태:** BOK 「금융·경제 스냅샷」 (`snapshot.bok.or.kr/dashboard/100a`) — 좌측 지표

## 1. 1단계가 물려주는 것과, 물려주지 **않는** 것

전체 브랜치 리뷰가 확인한 경계다. **이것을 모르고 2단계를 지으면 틀린 것을 만든다.**

### 1.1 7,804칸(26.4%)은 데이터베이스를 타지 않는다 ← 가장 중요

`src/verify/compare.ts` 가 평가 중에 `grids = oracle` 을 쓴다. 그 결과:

```
일치 셀의 86.8%   평가 중 인쇄값을 한 번 이상 읽는다
        30.1%   인쇄값을 값 자리에 넣는다
        26.4%   (7,804칸) SQL 을 아예 타지 않는다 — 통합문서 리터럴에만 의존
```

즉 **1단계 관문은 「셀별 번역」을 증명하고 「조립된 파이프라인」을 증명하지 않는다.**

`data/oracle` 은 **2025년 기준에 얼어붙은 값**이다. 그러므로:

> **2단계는 그 통합문서 리터럴을 물화하지 않으면 7,804칸이 2025 에 정적으로 남는다.**
> 「관문이 통과했으니 전부 살아 있는 계산이다」로 읽으면 **틀린다.**

#### 목록을 냈다 (2026-09-11) — 결론: **손으로 넣는 통계값은 없다**

`scripts/analyze-literals.mjs` + `scripts/analyze-literals-classify.mjs` 로 **추이적**
의존을 끝까지 따라갔다. 판정 규칙: 어떤 칸이 읽는 셀이 cellmap 에 있으면 그것도 계산되는
값이니 계속 내려가고, 없으면 **사람이 손으로 넣은 상수(잎)** 다.

```
검증칸 29,561
  잎에 의존하는 칸    3,999  (13.5%)
  의존 없는 칸       25,562
  서로 다른 잎          247
```

리뷰의 「7,804칸(26.4%)」은 **「SQL 을 안 타는 칸」**이라 더 느슨한 측정이었다. 계산된
셀을 읽는 칸도 거기 포함된다. 실제로 **손입력 상수까지 내려가는 칸은 3,999개**다.

잎 247개의 정체:

| 잎 | 개수 | 의존칸 | 무엇 |
|---|---|---|---|
| 작은 정수 | 83 | 376 | **VLOOKUP 열 번호**. `p128!C4..L4` 가 `2,3,4…11` 이다 |
| 문자 라벨 | 82 | 373 | **SUMIFS 조건·범주명** (`"총 계"`, `"전 산업"`, `"* 사회간접자본…"`) |
| 연도 상수 | 77 | 3,285 | 그래프 **축 시작 연도**(1970 이 15개)와 **앵커**(2025) |
| 수치 후보 | 5 | 25 | 아래 전수 |

**「수치 후보」 5개를 전부 확인했고, 4개는 통계값이 아니다:**

```
p178!B49 = 1929   영국이 고령화사회(7%)에 도달한 해   ← 역사 상수. 바뀌지 않는다
p178!B50 = 1942   미국                              ← 같음
p178!B51 = 1864   프랑스                            ← 같음
```
(분류기가 1960 미만이라 후보로 올렸을 뿐이다. `p178` 은 국가별 고령화 도달 연도 표다.)

**남은 진짜 구멍은 하나다:**
```
p23!C7 = 202401      p23!O7 = 202501      (경기종합지수, 월 시점. 의존칸 22)
p23!D7 = C7+1 …      p23!P7 = O7+1 …      월 사슬이 여기서 이어진다
```
**월 시점 씨앗 두 개가 손으로 박혀 있어 앵커를 따라가지 않는다.** 앵커가 2026 으로
가도 `p23` 은 2024·2025 월에 머문다. `part1_5`·`part3` 의 손타이핑된 `_시계열!B1` 과
**같은 부류**이고, 그때 Ruling 17 이 앵커를 주입해 해결한 것과 같은 방식으로 고친다.

#### 그래서 2단계가 할 일

1. **`p23` 의 월 씨앗 2개를 앵커에서 유도한다** (`앵커*100+1` 꼴). 의존칸 22.
2. 나머지 245개 잎은 **데이터가 아니므로 물화 대상이 아니다** — 열 번호·범주명·축 시작
   연도는 지면 서식이고, `layout.json` 에 담기면 된다.
3. **따라서 §1.1 이 우려한 「7,804칸이 2025 에 정적으로 남는다」는 성립하지 않는다.**
   앵커를 옮기면 `p23` 22칸을 뺀 전부가 따라 움직인다. 그 22칸도 1 로 해결된다.

### 1.2 대조 주장의 상한 — 586칸(2.0%)

인쇄값이 `0` 또는 `-` 라서, 조건을 「아무것도 안 맞는 값」으로 바꿔도 여전히 일치한다.
구조적 한계이고 없앨 수 없다. 반대 위험(오류를 `-` 로 덮어 통과)은 **없음이 확인됐다**
(`-` 418칸 중 오류-null 경유 0칸).

**화면에 미치는 영향:** `0`·`-` 로 표시되는 칸은 1단계 대조가 사실상 검증하지 못한다.
2단계에서 그 칸을 「검증됨」으로 표시하지 말 것.

### 1.3 부록·서식 3,364칸은 대조 대상이 아니다

외부 통합문서를 참조하지 않는 칸(Ruling 14). 화면에 낼 값이 아니라 책자 조판용이다.

### 1.4 면제 3칸 — 인쇄본이 틀린 곳

세종 순이동(`p18` 2칸 · `p140` 1칸). 인쇄본이 현재 KOSIS 의 정확히 2배.
**화면은 계산값(−47 등)을 보여주고, 인쇄본과 다르다는 사실을 감추지 않는다.**
`data/known-divergences.json` 이 사유·증거·결정자를 담고 있으니 그것을 읽어 표시한다.

## 2. 연도 규칙 (1단계에서 확립)

```
앵커(기준연도) → _시계열 사슬 평가 → 지면 연도 헤더 → SUMIFS 조건
```
13개 part 전부에서 앵커=2025 가 확정본 연도를 재현한다(236/0 → 268칸). 앵커를 2026 으로
옮기면 2,301칸이 따라 움직인다. **연도는 계산되며 얼어붙어 있지 않다.**

2단계가 얹을 것 — 사용자 요구:
- **기본값은 지표별 최신 공표 연도** (전역 한 해가 아니다)
- **기준연도 입력 시 지표별로 클램프**: 2025 를 넣었는데 그 지표 최신이 2024 면 2024 까지

**「지표별 최신 연도」의 정의는 1단계에서 실측으로 확정했다** (Ruling 16 보강):

| 갈래 | 최신 연도 |
|---|---|
| 연간표(4자리), 추계 아님 | `max(substr(prd_de,1,4))` |
| **추계표** | 산정에서 **제외** — `DT_1BPA001` 은 1970~2070 이다 |
| 월간표(6자리), 연 단위 표시 | **12개월이 모두 있는 마지막 연도** |
| 월간표(6자리), 월 단위 표시 | `max(prd_de)` 그대로 |
| OECD | dataset 별 `max(TIME_PERIOD)` — `PAG` 만 2024 |

107개 표 중 **26개가 2025 가 아니다**(2019 3 · 2023 5 · 2024 16 · 2026 1 · 2070 1).
클램프는 실제로 물린다. 추계표는 **추측하지 않고 목록으로 선언한다**
(`src/query/projections.ts`) — 「앵커보다 크면 추계」는 틀린다(월간 202601 이 반례).

**아직 구현 안 됨:** `latestYear`/`latestYears`/`clampYear`. 브리프가 이미 있다
(`.superpowers/sdd/…/task-9u9-brief.md` 의 초안은 면제 단위로 덮였으므로 다시 쓸 것).

## 3. 화면이 쓸 데이터

| 파일 | 무엇 | 비고 |
|---|---|---|
| `data/cellmap/*.json` | 셀별 질의 명세 | 열 이름 해석 완료. 수식 문자열 없음 |
| `data/layout.json` | 지면 구조 | `A1` 제목 195 · **`A2` 출처기관 177** · **`C2` 출처통계 144** |
| `data/gate-snapshot.json` | 관문 통과 시점 계산값 | 회귀와 개정을 구분하는 기준선 |
| `data/known-divergences.json` | 면제 | 사유·증거·결정자 |
| `data/oracle/*.json` | 인쇄값 | 정답표. **1.1 의 리터럴 원천이기도 하다** |

**`C2` 가 목업의 「카드 상단 출처통계」 값이다.** API 표 ID 를 뒤져 만들 것이 아니었다 —
책자가 이미 적어두고 있었다. **`A2` 가 없는 지면 18개, `A2` 가 `기준년도 -1`(출처가
아님)인 지면 3개는 빈칸으로 남긴다. 추정해 채우지 않는다.**

## 6. 파이프라인 — 갱신은 원데이터만으로 (2026-09-11 사용자 결정)

> **「업데이트는 PDF나 엑셀 의존적이지 않도록, 원데이터에서 바로 뽑아올수있도록 고려해서
> 파이프라인 설계. (그래프 또한 그래야함)」**

### 6.1 명세와 데이터를 가른다

```
        ┌ 한 번만 뽑는다 (명세 · 저장소에 동결) ─────────────────┐
작업본 엑셀 ──→ cellmap.json      셀별 질의 명세
작업본 엑셀 ──→ charts.json       차트 종류·계열 범위·축
작업본 엑셀 ──→ layout.json       지면 제목·출처기관·출처통계
확정본 엑셀 ──→ constants.json    수식이 아닌 상수 247개 (라벨·축 시작연도·조회 열번호)
발간 PDF   ──→ pdf-pages.json    인쇄된 표의 행·열 구성
발간 PDF   ──→ toc.json          Part › 장 › 절 › 지면
        └───────────────────────────────────────────────────┘

        ┌ 매월 갱신된다 (데이터) ─────────────────────────────┐
KOSIS·OECD API ──→ obs.sqlite
        └───────────────────────────────────────────────────┘

obs.sqlite + cellmap + constants  ──→  **계산값**  ──→  화면(표·그래프)
```

**명세는 회차마다 한 번 사람이 갱신하고, 수치는 매월 자동으로 바뀐다.**
화면이 엑셀이나 PDF 를 다시 읽는 경로는 없다.

### 6.2 지금 위반하고 있는 것

`web/build-data.mjs` 가 값을 **`gate-snapshot.json`** 에서 읽는다. 그것은 관문 통과 시점의
동결 스냅샷이므로 원데이터를 다시 받아도 화면이 바뀌지 않는다. 게다가 `verifyCellMap` 은
평가 중 `grids = oracle`(확정본)을 읽어, 전체 리뷰가 지적한 대로 **일치 셀의 26.4%가
DB 를 아예 타지 않는다.**

### 6.3 고치는 방법 — 리터럴 247개를 명세로 물화한다

리터럴 의존을 실측했을 때(§1.1) 잎이 **247개**뿐이고 거의 전부가 데이터가 아니었다:
```
 83  작은 정수   VLOOKUP 열 번호 (p128!C4..L4 = 2,3,4…11)
 82  문자 라벨   SUMIFS 조건·범주명 ("총 계", "전 산업")
 77  연도 상수   그래프 축 시작(1970 등)과 앵커
  5  수치 후보   4개는 역사 상수(영·미·프 고령화 도달 연도), 1건은 p23 월 씨앗
```
**이 247개를 `data/constants.json` 으로 물화하면 확정본이 실행 경로에서 빠진다.**
그러면 계산에 필요한 것은 `cellmap + constants + obs.sqlite` 뿐이다.

확정본(`data/oracle/`)은 **검증에만** 쓴다 — 그것이 원래 역할이다.

### 6.4 그래프도 같다

`charts.json` 은 **범위 명세**(`'p8'!$B$4:$CX$4`)만 담는다. 그 범위의 **값은 계산값에서
가져온다.** 따라서 원데이터가 갱신되면 그래프도 함께 움직인다. 이미 그렇게 만들었으나
값의 출처가 스냅샷이라 끊겨 있었다 — 6.3 으로 이어붙인다.

### 6.5 표는 인쇄본 구성을 따르고 값은 계산값에서

사용자: 「엑셀에 값이 있는 셀 중에는 참고를 위해서 넣은 값도 많아서 ... 굳이 책자 표에
넣지 않아도 되는 값이 많음」 · 「PDF 에 최종적으로 들어간 표를 기준으로」

실측: 목차 202쪽이 PDF 에서 **100% 찾아졌고**(쪽번호는 바닥글에서 읽음), **표가 있는 쪽
148개 · 표 없는 쪽(그래프만) 54개 · 인쇄된 표 280개**. 216쪽 OECD 는 `14행 × 7열`,
머리가 `["국가명","’20년",…,"’25년"]` — 엑셉 시트는 38개국에 열이 훨씬 많다.

그래서 **PDF 표는 「무엇을 보여줄지」의 명세로만 쓰고, 값은 계산값에서 가져온다.**
PDF 값을 그대로 쓰면 매월 갱신이 표에 반영되지 않는다.

진행 순서 (사용자 지시):
1. PDF 표의 머리행·첫 열을 엑셀 라벨과 **자동 매칭**
2. 매칭된 지면은 **인쇄본 구성**으로 표를 그린다
3. **안 맞는 지면은 목록으로 뽑아 보고한다** — 추측으로 채우지 않는다

PDF 값과 계산값이 **다른 곳도 함께 보고한다.** 인쇄본과 현재 원자료가 갈린 자리이고,
세종 3칸 같은 건이 또 있을 수 있다.

### 6.6 표는 접어 둔다 (사용자 결정)

기본은 그래프만. 표는 접혀 있고 「표로 보기」로 펼친다. 머리의 **검수 모드**를 켜면 모든
지면에서 표가 펼쳐진 채로 열리고 브라우저에 기억된다. 검수가 끝나면 끄면 그래프만 남는다.

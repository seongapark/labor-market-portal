## 1. 무엇을 만드는가

**지표 카드 포털**이다. 한국은행 「금융·경제 스냅샷」(snapshot.bok.or.kr)과 같은 형태로,
좌측 주제 트리와 카드 그리드로 지표를 보여준다. 카드 하나가 책자의 지면 하나에 대응한다.

책자 지면 재현(인쇄용 레이아웃)은 **같은 데이터의 두 번째 뷰**이며 나중 단계다.
데이터 계층과 지면 메타를 완전히 공유하고 렌더러만 다르다.

| | 지표 카드 뷰 (먼저) | 책자 뷰 (나중) |
|---|---|---|
| 배치 | 좌측 주제 트리 + 카드 그리드 | 지면당 1페이지, 인쇄 CSS |
| 주역 | 차트 크게, 표는 접기 | 표 크게, 차트는 지면 위치 그대로 |
| 기간 | 카드별 기간 버튼 | 기준연도 하나로 전 지면 통일 |

### 만들지 않는 것

- **발간본 재현(판본 아카이브)** — 「2024 발간본을 그때 인쇄된 수치 그대로」 보여주는 기능은
  범위 밖이다(2026-09-10 사용자 결정). 시점 조작은 **시계열 창 이동** 하나뿐이다.
  소급 개정된 과거 수치는 현재 값으로 나오며, 그것을 감수한다.
- **지표 해설 문구** — 카드에는 싣지 않는다(2026-09-10 사용자 결정). 카드는 제목·대표
  수치·차트·표·출처통계만 둔다.
- **카드 하단 부가 기능** — 표 전체 보기·CSV·이미지 저장 버튼을 두지 않는다.

## 3. 목표 구조

```
[수집]  Cloudflare Workers (Cron Triggers)
  KOSIS Open API  ─┐
  OECD SDMX API   ─┼─▶  D1 : obs 테이블 (long-format 그대로)
  수기 시트 업로드  ─┘
                          │
[집계]                    ▼
  cellmap (셀 → 질의 명세)  ─▶ 질의 실행 ─▶ 지면 JSON · 지표 JSON
                          │
[검증]                    ▼
  확정본 캐시값 32,925셀과 전건 대조   ← 관문
                          │
[배포]                    ▼
  Cloudflare Pages (React + Vite) — 정적 자산 + JSON
```

**Cloudflare로 통일한다**(2026-09-10 사용자 결정). D1 + Workers + Pages.
프론트엔드는 **React + Vite → Cloudflare Pages**. Vercel을 섞으면 업체가 둘로 갈리는데
그 대가로 얻는 것이 없다.

### 왜 Excel이 파이프라인에서 빠지는가

앵커를 연도마다 바꿔가며 Excel COM으로 재계산하는 방법도 가능하고, 검증된 기계를 그대로
쓴다는 장점이 있다. 그러나 **Excel이 깔린 PC가 필요해 클라우드 자동화가 불가능**하다.
매월 무인 갱신이 목표이므로 SQL 이관을 택했다(2026-09-10 사용자 결정).

이관의 최대 위험은 「인쇄본과 수치가 어긋나는 것」인데, **확정본 13개에 32,925개 셀의
정답이 캐시값으로 이미 박혀 있다.** 정답표가 있으므로 이관은 검증 가능한 작업이 된다.
이것이 SQL 이관을 택할 수 있는 근거다.

### 브라우저는 D1을 직접 질의하지 않는다

빌드 타임에 질의를 실행해 **정적 JSON**을 만들고 Pages가 그것을 낸다. 카드 202개에
전체 시계열을 담아도 총량이 작다. 검색 인덱스도 빌드 타임에 만든다.
런타임 Worker API는 다운로드·질의가 실제로 커진 뒤에 붙일 여지로 남긴다.

## 4. 데이터 계층

### 4.1 스키마

KOSIS API 응답 스키마를 그대로 받는다. 별도 설계를 하지 않는다.

```sql
CREATE TABLE obs (
  table_id   TEXT NOT NULL,      -- 시트명 = KOSIS 표ID
  prd_de     TEXT NOT NULL,      -- 기간코드 (연 4자리 / 반기·월 6자리)
  itm_id     TEXT,
  itm_nm     TEXT,               -- 항목명 (취업자 · 고용률 …)
  c1_obj_nm  TEXT, c1 TEXT, c1_nm TEXT,
  c2_obj_nm  TEXT, c2 TEXT, c2_nm TEXT,
  c3_obj_nm  TEXT, c3 TEXT, c3_nm TEXT,
  unit_nm    TEXT,
  dt         REAL,
  PRIMARY KEY (table_id, prd_de, itm_id, c1, c2, c3)
);
CREATE INDEX obs_lookup ON obs (table_id, prd_de, itm_nm);
```

- **`prd_de` 는 TEXT로 둔다.** 반기 표는 6자리(`202401`)이고, 연간 표인데 6자리인 것도
  있다(`DT_1DE7108S` 는 조사시점이 8월이라 `202508`). 숫자로 바꾸면 이 구분이 무너진다.
- OECD는 별도 테이블(`oecd_obs`)로 둔다. 차원 이름이 KOSIS와 다르다.
- 수기 시트는 `manual_obs` 로 long 변환해 적재한다. wide 시트는 변환표를 함께 둔다(§4.4).

### 4.2 SUMIFS → 질의 번역

수식이 전부 한 가지 골격이다(2026-09-10 실측, part1_3·part1_9·part3·part1_5·part1_8 확인).

```
SUMIFS([1]DT_1DA7012S!$C:$C,          ← 값 열
       [1]DT_1DA7012S!$H:$H, TEXT(C$6,"0"),   ← 연도 (헤더 행 참조)
       [1]DT_1DA7012S!$I:$I, "계",            ← 분류 조건
       [1]DT_1DA7012S!$B:$B, "계",
       [1]DT_1DA7012S!$G:$G, "취업자")
```

```sql
SELECT SUM(dt) FROM obs
 WHERE table_id = 'DT_1DA7012S' AND prd_de = :year
   AND c1_nm = '계' AND c2_nm = '계' AND itm_nm = '취업자'
```

조건 쌍은 **2~4개**뿐이다(3쌍 1,014 · 4쌍 577 · 2쌍 36 — part1_3 기준).
조건값은 세 종류다: 연도(`TEXT(셀,"0")`) · 문자열 리터럴 · 셀 참조(행 라벨·헤더).
조합 연산은 `+SUMIFS`(합산)와 `A/(SUMIFS+SUMIFS)%`(구성비) 둘.
OECD·별도데이터 참조는 `IF(SUMIFS(...)=0,"-",SUMIFS(...))` 가드가 씌워진 같은 골격이며,
평균이 필요한 곳은 `SUMIFS/COUNTIFS`, 단위 환산은 `/1000` 이다.

**파서 산출물은 셀별 질의 명세(`cellmap`)다.** 코드를 생성하지 않고 데이터를 만든다.

```json
{ "page": "p42", "cell": "B7",
  "expr": { "op": "sum", "args": [
    { "table": "DT_1DA7001S", "value": "dt",
      "where": { "prd_de": "@year", "c1_nm": "계", "itm_nm": "경제활동인구" } } ] } }
```

### 4.3 표시 라벨과 조회 키를 분리한다

각 행은 화면에 보일 `label` 과 연도별 원본 조회키 `key_by_period` 를 따로 갖는다.

```json
{ "label": "제조업",
  "key_by_period": { "~2019": "제조업(9차 C)", "2020~": "제조업" } }
```

분류가 개편되면 **조회키만 한 줄 추가하고 라벨은 건드리지 않는다.**
인수인계문서 01이 「통일하려면 표시 라벨과 조회 키를 분리해야 한다 — 사용자 판단으로
내년으로 미룸」이라 적어 둔 숙제가 이 구조로 풀린다.

### 4.4 자동화가 닿지 않는 자리

④ 예외 지면 8개(p35 · p67 · p83 · p122_123 · p128 · p132 · p161 · p187)와 기준시점
미상 23쪽은 API로 오지 않는다. **한 덩어리로 따로 다룬다.**

- 수기 wide 시트를 `manual_obs` 로 옮기는 **변환표**를 지면별로 적는다(행 라벨 → 좌표).
- 변환표는 사람이 쓰고 사람이 검수한다. 439개 셀이므로 검수 가능한 분량이다.
- p133~p135는 2026-09-01 시점 「전년 유지 확정」이다. 근로복지공단 「통계연보」 원데이터를
  수집해 연동을 붙이는 것이 다음 발간 목표이며, 그 전까지는 전년 값 유지로 표시한다.

## 5. 검증 — 이 설계의 관문

**확정본 13개가 정답표다.** 작업본에서 수식이 있던 좌표 **32,925곳**에 확정본은 그 수식이
계산한 값을 갖고 있다(동결 도구가 수식을 값으로 치환했다). 그 좌표 하나하나를 대조 대상으로 삼는다.

1. 확정본에서 전 시트 전 셀의 값을 읽는다(openpyxl **읽기 전용**, 저장하지 않는다).
2. 같은 좌표를 `cellmap` 질의로 계산한다.
3. 전건 비교한다. 허용 오차는 **표시 자리수 기준**으로 정한다(소수 1자리 표시 셀은 0.05).
4. **불일치 0이 될 때까지 이관을 완료로 보지 않는다.**
5. 지면별 일치율 리포트를 저장소에 남긴다.

이것이 통과하면 「인쇄본과 같은 수치」가 주장이 아니라 증명이 된다.

> **절대 규칙: 집계표를 openpyxl로 열었다 저장하지 말 것.** 저장만 해도 차트가 파손되는데
> 파일은 정상적으로 열려서 잡히지 않는다. 검증은 읽기만 한다.

지면으로 만들면서 **결함 11건**이 나왔고, 그 전부가 여기 규칙의 근거다.

### 6.2 해석기 설계 원칙

위 11건 중 **1·2·3·4·9는 모두 제가 넣은 추측 규칙이 원인**이었다. 202개 지면은 구조가
제각각이라 휴리스틱은 반드시 어딘가에서 깨진다. 따라서:

1. **원본이 명시하는 것만 읽는다.** 계열의 차트 종류는 추측하지 않고 XML 블록에서 읽는다.
2. **애매하면 후보를 점수 매겨 고른다.** 「첫 번째로 맞는 것」을 쓰지 않는다.
3. **끊는 조건을 명시한다.** 한 시트에 표가 여럿인 것이 정상이다.
4. **수치는 수치로 옮긴다.** 형 변환이 값을 조용히 죽인다.
5. **202개 지면 전수를 기계로 대조한다.** 눈으로 9개를 봐서 11건이 나왔다.

## 7. 지면별 판단표

원본 엑셀이 차트 종류나 표 구성을 잘못 고른 지면이 있다. **코드에 조건문을 쌓지 않고
데이터로 적는다.** 264개 차트에는 이런 표가 필요하다.

### 7.1 차트 판단표

```json
{ "40":  { "type": "pie", "col": 1,
           "rows": ["취업자", "실업자", "비경제활동인구"],
           "total": "15세이상인구",
           "note": "원본 파이는 경제활동인구·취업자·실업자를 한 파이에 넣어 합이 전체의 두 배였다." },
  "195": { "type": "pie", "transpose": true } }
```

**p40은 발간본 원본에 오류가 있다**(2026-09-10 확인). 파이 조각이
`경제활동인구 29,598.9 / 취업자 28,768.9 / 실업자 830` 인데 **경제활동인구 = 취업자 + 실업자**라
합이 전체의 두 배이고 취업자가 49%로 표시된다. 15세이상인구를 전체로 두고 세 조각으로
바로잡았다(2026-09-10 사용자 결정).

```
취업자 28,768.9 + 실업자 830 + 비경제활동인구 16,163.5 = 45,762.4 = 15세이상인구   (차 0)
취업자 조각 62.9% = 같은 지면 표의 고용률 62.9
```

정정 사유는 **책자 뷰의 `주`** 로만 표시한다. 카드에는 싣지 않는다.

### 7.2 표 분할 판단표

```json
{ "86": [{ "title": "임금 (원)",       "match": "임금총액|급여" },
         { "title": "근로시간 (시간)", "match": "근로시간" }] }
```

p86은 **단위가 다른 두 표가 한 표로 합쳐져** 있다(원 6행 · 시간 5행).

### 8.2 차트 규칙

- **이중축을 쓴다**(2026-09-10 사용자 결정). 막대는 좌축·0부터, 선은 우축·자기 최소~최대에
  10% 여유. 축마다 어느 계열인지 색 표식을 붙인다. 264개 중 78개가 막대+선 혼합이다.
- **증감은 별도 플롯을 만들지 않는다.** 증감 계열이 우축을 차지하고, **화살표를 그 값의
  좌표에 찍는다**(▲ 상승 · ▼ 하락). **0.0은 `-`** 로 표시한다.
- **선은 시간축에서만 쓴다.** 시도·국가처럼 순서 없는 범주를 선으로 잇지 않는다.
- **최근 시점 x라벨은 무조건 그린다**(굵게·진하게). 앞 라벨과 부딪히면 앞을 뺀다.
  선 끝점에 최신 값을 직접 라벨로 붙인다.
- **시도명은 2글자로 통일한다**: 서울 · 부산 · 대구 · 인천 · 광주 · 대전 · 울산 · 세종 ·
  경기 · 강원 · 충북 · 충남 · 전북 · 전남 · 경북 · 경남 · 제주.
  `강원특별자치도`·`전북특별자치도`·`제주특별자치도` 도 같은 약칭을 쓴다.
- **2025년까지는 `전남광주통합특별시`를 제외하고 광주·전남을 따로 둔다**
  (2026-09-10 사용자 결정). 이 행은 2025년부터만 존재하는데 광주·전남 행이 함께 남아
  있어, 넣으면 **이중계상**된다. 제외로 그 문제가 함께 해소된다.
  2026년 이후 회차에서 통합시로 갈지는 그때 다시 정한다.
- **집계와 개별을 구분한다.** 계열이 1개면 `계`·`OECD 평균`은 진한 남색(`#17518f`),
  `한국`은 주황(`#eb6834`). 계열이 2개 이상이면 색이 식별색과 싸우므로 **바탕 밴드**로 구분한다.

### 8.3 색과 활자

계열 식별색은 검증기(`dataviz` 스킬 `validate_palette.js`)를 통과한 값만 쓴다.

| 역할 | 값 | 검증 |
|---|---|---|
| 계열 1 (막대 기본) | `#8ec46b` 연두 | 주황과 CVD ΔE 8.8 · 정상시야 24.3. 대비 2.05 → **표·라벨 병기로 해제** |
| 계열 2 | `#eb6834` 주황 | 〃 |
| 계열 3 | `#4a3aa7` 보라 | **파랑을 증감 전용으로 비우기 위해** 파랑에서 옮겼다 |
| 집계 강조 | `#5a8f30` 진한 연두 | 계열 1과 같은 색조의 명도 단계. 새 색조가 아니라 강조다 |
| 증감 상승 | `#c0392b` | 계열색과 분리 |
| 증감 하락 | `#0b6bd6` 채도 높은 파랑 | 계열 1과 정상시야 **ΔE 35.4**, 대비 3:1 통과 |

**파랑은 증감 하락 전용이다.** 계열색에 파랑을 두지 않는다. 계열 3이 파랑이면 3계열
차트에 증감이 함께 찍힐 때 같은 문제가 재발하므로, 규칙으로 비워 둔다.

**막대 기본색이 파랑에서 연두로 옮겨온 경위**(2026-09-10 사용자 지적 2회):
막대가 파랑(`#2a78d6`)이면 같은 차트에 찍히는 **증감 하락 화살표(파랑)가 막대에 묻힌다.**
증감은 계열이 아니라 별개 부호인데 같은 지면에 함께 나오므로 **계열끼리의 구분만이 아니라
증감 두 색과의 구분도 함께 검증해야 한다** — 이것이 여기서 얻은 원칙이다.

1차로 `#22a06b`(초록)로 옮겼으나 여전히 화살표가 덜 도드라져,
**막대는 더 연하게(연두) · 증감 파랑은 채도를 높이는** 방향으로 다시 잡았다.
그 결과 막대-화살표 분리도가 **ΔE 28.6 → 35.4** 로 올랐다.

증감 하락도 `#4a9fe0` → `#2b7fc4` → `#0b6bd6` 로 두 번 진해졌다. 화살표가 8px짜리 작은
도형인데 `#4a9fe0` 의 밝은 배경 대비가 **2.87:1로 3:1 미달**이었던 것이 1차 이유다.

**연두는 밝은 배경 대비가 2.05로 3:1에 미달한다.** 검증기의 relief 규칙에 따라
**범례 라벨과 표를 항상 함께 두는 것이 필수 조건**이다 — 이 둘을 없애면 규칙 위반이 된다.
「막대를 더 연하게」의 대가이며, 알고 택한 값이다.

### 8.4 표

```json
   "tables": ["DT_118N_LCE205→LCE305"],
   "affected_items": ["C", "D", "E", "L", "N"],
   "note": "제10차 한국표준산업분류를 반영하여 공표함에 따라 제9차로 작성된 2019년 이전 자료와 비교 시 유의",
   "pages": ["p101", "p102", "p103", "p104,105"] }]
```

- 화면은 단절 연도에 **한 줄 ⚠ 경고**를 띄운다. 상세 문구는 책자 뷰에서만 펼친다.
  이것은 부수 정보가 아니라 **「이 연도를 넘어 비교하면 틀린다」는 경고**이므로 지우지 않는다.
- 포괄범위가 실제로 달라진 5개 산업(C·D·E·L·N)은 그 행에만 따로 경고를 붙인다.
- 새 개편이 생기면 **수집 목록에 후속표 한 줄 + 이 파일에 한 줄**이고 화면 코드는 고치지 않는다.
- **슬라이더를 과거로 많이 밀면 단절을 여러 개 넘어 표가 점점 비어 간다.** 그래서 슬라이더
  범위를 무한정 넓히지 않고 실용 범위(최근 10년)로 둔다.

## 10. 매월 갱신 운영

Cloudflare Workers Cron Triggers로 수집한다. 실행 후 `cellmap` 질의를 다시 돌려 JSON을
만들고 Pages에 배포한다.

- **변화 0건을 실패로 판정하지 않는다.** 9·10·11월에는 새로 공표되는 것이 없다(§2).
  「변화 0건」과 「수집 실패」를 구분해 기록한다.
- 외부 장애는 **기한과 함께** 적어 두고, 기한이 지나거나 그 수집기가 되살아나면 일부러
  실패시킨다(고용데이터아카이브 `KNOWN_DOWN` 관례를 그대로 가져온다).
- **KOSIS 표 승계 가드**: 표의 최신 기간이 예상과 어긋나면 표 id를 짚으며 실패한다.
  분류 개편으로 표가 갈리는 사고를 잡는 장치다.
- **API 함정**(인수인계문서 01 실측)을 수집기가 지켜야 한다.
  - 반기 표의 기간코드는 6자리(`202401`). 5자리로 요청하면 `err=30 데이터 없음`.
  - **연간 표인데 기간코드가 6자리인 것이 있다.** `DT_1DE7108S` 는 `2015~2025` 로 요청하면
    최신연도가 **조용히 누락**되고 `201501~202512` 로 요청해야 온다. 에러가 나지 않는다.
  - `DT_1DA7107S` 는 `objL3` 까지 필수.
